验证用例 · 开发场景（AI 建模偏离意图）

一、问题重定义

不是「AI 写错」（语法错、注入、边界），而是：

AI 建了一个模型，跟你想的不是一回事。你能看出「不对」，但说不清哪里不对，也说不清它怎么变成这样的。

这个问题的本质：

· 你有一个意图模型（脑子里想要的东西）
· AI 有一个实现模型（它以为你要的东西）
· 两者偏离，且偏离过程不可见

反思要解决的，就是把偏离过程显性化。

二、具体案例

背景

你想让 AI 写一个「任务提醒」功能。

你脑子里的意图：

用户给任务设个时间，到点提醒。

AI 的实现：
建了一整套 Task → Schedule → Notification → Channel → Template → RetryPolicy 的表和类，几十个文件。

你一看就懵了：这跟我说的不是一回事，但我不知道它为什么走了这么远。

Day 1：反思

第一步：拆解（纸）。先把 AI 的实现拆成它的推理链：

```
结论：AI实现符合我的意图
前提一：AI理解的「任务提醒」= 我的「任务提醒」
前提二：AI会把复杂度和需求规模匹配
```

第二步：检验（纸）。拿反例打每一条前提：

```
打「AI理解的提醒=我的提醒」
→ 反例：AI加了 RetryPolicy、Channel、Template，我根本没提
→ 结论：AI把「提醒」理解成了「企业级通知系统」

打「AI会把复杂度和需求规模匹配」
→ 反例：我只说了一句话，它建了几十张表
→ 结论：AI默认往「完备」方向建模，不往「最小」方向建模
```

第三步：固化。把可疑前提改写成下次动手前的提醒：

```
reflect commit "让AI写功能前先给复杂度预算：最多几个文件、几个概念" --revises "AI会把复杂度和需求规模匹配"
reflect commit "需求里的抽象词必须先钉死边界" --revises "AI理解的提醒=我的提醒"
```

Day 30：新事件

你又让 AI 写「用户积分」功能。它开始建 Point → Rule → Event → Ledger → Settlement……

此时：

```
reflect check "让AI写用户积分功能，抽象词和边界要说清"
→ 命中（25%）：需求里的抽象词必须先钉死边界
→ 命中（19%）：让AI写功能前先给复杂度预算：最多几个文件、几个概念
```

你被拦住了。 你在它动手前先说：「只要一个字段加一次加减，最多一个文件。」

三、这个案例的关键差异

维度 上次的「AI乱写」 这次的「建模偏离」
问题 代码错 模型错
你能察觉吗 能，一跑就知道 能察觉「不对」，但说不清
难点 修 定位偏离点
反思对象 代码 AI的推理链
固化产出 检查清单 约束条件 + 词汇边界

四、这类问题的反思要点

核心：不要反思「AI为什么写错」，要反思「我在哪个环节没把意图传清楚」。

因为 AI 建模偏离，通常来自三个断点：

1. 词汇断点：你说的词 ≠ AI 理解的词（「提醒」 vs 「通知系统」）
2. 规模断点：你没说复杂度上限，AI 默认往完备走
3. 边界断点：你没说「不要什么」，AI 就全都要

反思要固化的，就是这三类断点的补丁。

五、验证清单

```
□ 1. 存得进：这条规则按存储的记法写得下去
□ 2. 召得回：下次AI又要「过度建模」时，check 能命中
□ 3. 拦得住：命中后，你在它动手前就加了约束
```

三条全过 = 可用。

六、可以复用的规则长什么样

```
- 抽象词必须先钉边界（「提醒」→ 到点弹窗，不含多渠道）
- 每次下需求先给复杂度预算（几个文件、几个概念）
- 先让AI说它打算建什么模型，再让它写代码
- 需求里主动写「不要什么」，比写「要什么」更重要
```

每条都来自一次真实偏离。规则句子里带上事件里会出现的词，才召得回。

七、一句话

AI 建模偏离，不是它写错，是你没在词汇、规模、边界上钉死。反思就是把这次的偏离拆开，找出断点，固化成下次动手前的约束。
