通用反思程序 · 极简版设计

一、核心理念

反思 = 把结论拆成前提，检验前提，把修正后的前提固化成规则。

一句话概括整个系统。其余全是它的实现细节。

二、系统架构

```
┌─────────────────┐      ┌──────────────────────┐
│   Skill         │      │   命令行管道          │
│  （反思逻辑）    │◄────►│  （知识图谱维护）      │
│                 │      │                      │
│  · 拆解          │      │  · 存储               │
│  · 检验          │      │  · 检索               │
│  · 固化          │      │  · 提醒               │
└─────────────────┘      └──────────────────────┘
```

· Skill：负责”怎么想“——三个动作的思考质量
· 命令行：负责”记住什么“——结构持久化 + 下次检索提醒

三、三个动作

动作 1：拆解

把结论还原成”它依赖的前提“。

```
输入：一个结论（Claim）
动作：
  - 写下结论
  - 问：它依赖哪些前提？
  - 写下 1~3 个前提（Premise）
输出：Claim → depends_on → Premise
```

动作 2：检验

对每个前提找反例。

```
输入：前提
动作：
  - 问：这个前提在什么情况下不成立？
  - 找反例
  - 有反例 → 标记”可疑前提“
  - 无反例 → 保留
输出：前提 + 反例（或”未发现反例“）
```

动作 3：固化

把修正后的前提写成规则。

```
输入：可疑前提 + 反例
动作：
  - 改写成一条可执行的 Rule
  - 存进知识图谱
输出：Rule（供下次检索）
```

四、数据结构

三种节点

节点 含义 例子
Claim 结论（我以为对的东西） ”被收编对IP不利“
Premise 前提（它依赖的东西） ”收编=失去独立性“
Rule 固化后的规则 ”收编是否有利，取决于是否要求闭嘴“

两种边

边 含义
depends_on Claim 依赖 Premise
revises Rule 修正 Premise

结构示意

```
Claim ──depends_on──► Premise
                         │
                      revises
                         │
                         ▼
                       Rule
```

五、最小工作流

```
事件发生（被否定/结果不符）
        │
        ▼
   ┌─────────┐
   │ 1. 拆解  │  写下结论 + 前提
   └────┬────┘
        ▼
   ┌─────────┐
   │ 2. 检验  │  找反例 → 标记可疑前提
   └────┬────┘
        ▼
   ┌─────────┐
   │ 3. 固化  │  改写为规则，存图
   └────┬────┘
        ▼
   下次遇到类似事件 → 检索规则 → 主动提醒
```

六、命令行接口

```
reflect add <claim>              记下结论
reflect dep <claim> <premise>    记下依赖关系
reflect test <premise>           检验前提（录入反例）
reflect commit <rule>            固化为规则
reflect check                    检索相关规则，主动提醒
```

五个命令，覆盖完整闭环。

七、完整示例

事件：我说”被收编对IP不利“，被人否定。

1. 拆解

```
reflect add ”被收编对IP不利“
reflect dep ”被收编对IP不利“ ”收编=失去独立性“
reflect dep ”被收编对IP不利“ ”失去独立性=信任崩塌“
```

2. 检验

```
reflect test ”收编=失去独立性“
→ 反例：分析师转顾问，信息更准、公信力没掉
→ 标记：可疑前提
```

3. 固化

```
reflect commit ”收编是否有利，取决于是否要求闭嘴“
```

下次触发：遇到”收编/合作/进入体系“类事件

```
reflect check
→ 提示：”收编是否有利，取决于是否要求闭嘴“
```

八、被砍掉的东西（以及为什么）

砍掉 理由
必要条件/充分条件 是”检验前提“的一种问法，不是独立步骤
找替代解释 是”检验前提“的方式之一，合并
框架识别 就是”更底层的前提“，用 Premise 表达
弱点标记 就是”反复出现的坏前提“，Rule 的反面
触发器 是查询逻辑，写在命令行里，不是数据
多余的节点/边类型 3 节点 + 2 边已经够表达一切

九、为什么这个结构够用

1. 前提是反思的命门——所有错误都藏在没写出来的前提里
2. 反例是唯一有效的检验——没有反例的反思是自我安慰
3. 规则 + 检索是复利的来源——不复用的反思等于白反思

其余一切都是这三个的包装。砍到骨头，才跑得动。

十、落地路径（建议）

1. 先做命令行 + 文件存储（JSON/YAML 即可，不必上真图数据库）
2. Skill 先只做动作 1（拆解）——最容易见效
3. 动作 2 检验——可以先人工，跑通再自动化
4. 动作 3 固化 + check 检索——形成闭环，价值才显现

先跑通闭环，再谈优化。
