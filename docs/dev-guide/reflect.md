通用反思程序 · 极简版设计

一、核心理念

反思 = 把结论拆成前提，检验前提，把修正后的前提固化成规则。

一句话概括整个系统。其余全是它的实现细节。

二、系统架构

```
┌─────────────────┐      ┌──────────────────────┐
│   Skill         │      │   命令行管道          │
│  （反思逻辑）    │─────►│  （规则表维护）        │
│                 │      │                      │
│  · 拆解          │      │  · 存储               │
│  · 检验          │      │  · 检索               │
│  · 固化          │      │  · 提醒               │
└─────────────────┘      └──────────────────────┘
```

· Skill：负责「怎么想」——三个动作的思考质量，不写代码
· 命令行：只接最后一步的产物——规则；以及动手前的检索

中间的箭头是单向的：思考进程序的东西只有一样，规则。程序不回填思考过程。

三、三个动作

动作 1：拆解

把结论还原成它依赖的前提。

```
输入：一个结论（Claim）
动作：
  - 写下结论
  - 问：它依赖哪些前提？
  - 写下 1~3 个前提（Premise）
输出：结论 → 前提，落在纸上或规格里
```

动作 2：检验

对每个前提找反例。

```
输入：前提
动作：
  - 问：这个前提在什么情况下不成立？
  - 找反例
  - 有反例 → 标为可疑前提；无反例 → 保留
输出：可疑前提 + 反例，同落在纸上
```

动作 3：固化

把修正后的前提写成规则，这是唯一进程序的一步。

```
输入：可疑前提 + 反例
动作：
  - 改写成一条可执行的 Rule，句子里带上事件里会出现的词
  - 连同它修正的前提一起记下来
输出：Rule（供下次检索）
```

四、程序维护的数据

只有规则表。一条规则两个字段：

字段 含义 例子

text 修正后的前提，写成可执行的句子 「收编是否有利，取决于是否要求闭嘴」

revises 这条规则修正的前提 「收编=失去独立性」

`revises` 不是给程序推理用的，是给召回补词的：规则的句子未必带全下次事件里会出现的词，它修正的那句前提往往带着。

存档是一个 JSON 文件，默认 `reflect.json`。

五、最小工作流

```
事件发生（被否定/结果不符）
        │
        ▼
   ┌─────────┐
   │ 1. 拆解  │  写下结论 + 前提（纸）
   └────┬────┘
        ▼
   ┌─────────┐
   │ 2. 检验  │  找反例，标可疑（纸）
   └────┬────┘
        ▼
   ┌─────────┐
   │ 3. 固化  │  改写为规则，存下来
   └────┬────┘
        ▼
   下次遇到类似事件 → check → 主动提醒
```

六、命令行接口

```
reflect commit <规则> [--revises <前提>]...   固化为规则
reflect check [事件]                          检索相关规则，主动提醒
```

两条命令，一进一出：进的是固化好的规则，出的是动手前的提醒。拆解与检验不设命令——它们是思考，让程序管工序只会让人少记一次。

七、完整示例

事件：我说「被收编对IP不利」，被人否定。

1. 拆解（纸）

结论「被收编对IP不利」，它依赖两条前提：「收编=失去独立性」「失去独立性=信任崩塌」。

2. 检验（纸）

拿反例打「收编=失去独立性」：分析师转顾问，信息更准、公信力没掉。打中，标为可疑。

3. 固化

```
reflect commit "收编是否有利，取决于是否要求闭嘴" --revises "收编=失去独立性"
```

下次触发：遇到「收编/合作/进入体系」类事件

```
reflect check "要不要进入体系、被收编、谈合作"
→ 命中（10%）：收编是否有利，取决于是否要求闭嘴
```

八、被砍掉的东西（以及为什么）

砍掉 理由

结论节点 Claim 拆解是思考，写在纸上；召回时用不到它

依赖边 depends_on 同上，只服务拆解过程

可疑标记 suspect 检验的中间状态；登记它等于让程序管工序

反例 counterexample 规则那句话里已经带上理由；程序不拿它做计算

add / dep / test 三条命令 只为上面四样存在

必要条件/充分条件 是「检验前提」的一种问法，不是独立步骤

找替代解释 是「检验前提」的方式之一，合并

框架识别 就是「更底层的前提」，用前提表达

弱点标记 就是「反复出现的坏前提」，规则的反面

触发器 是查询逻辑，写在命令行里，不是数据

多余的节点/边类型 已经退化成一个字段：规则带上它修正的前提

九、为什么这个结构够用

1. 前提是反思的命门——所有错误都藏在没写出来的前提里
2. 反例是唯一有效的检验——没有反例的反思是自我安慰
3. 规则 + 检索是复利的来源——不复用的反思等于白反思

其余一切都是这三个的包装。砍到骨头，才跑得动。

十、落地路径

1. 先把规则表与检索跑通（一个 JSON 文件即可，不必上真图数据库）
2. 动作 1 与动作 2 用纸或规格，不写代码
3. 动作 3 固定成一条 `commit`，检索固定成一条 `check`，闭环合上
4. 拿到真实环境里跑一轮，看召得回与拦得住是否成立
