# 维护

## 当前状态与第一步

设计已成文，CLI 还没写。`src/cli/` 眼下只有 `Cargo.toml` 和 `TODO.md`。

按 `TODO.md` 的顺序动手：先把测试样例重新设计、写一遍，再放到「工作云」平台的真实需求上跑一次。写代码时守住三件事——存储先用单个 JSON 文件，不上图数据库；先只做拆解一个动作，跑通了再加检验与固化；命令保持五条。

## 闭环是否还在

reflect 有没有用，看三件事能不能过：这次偏离拆不拆得成 AI 的推理链，也就是存得进；下次 AI 又要过度建模时 check 能不能命中，也就是召得回；命中之后你有没有在它动手前加上约束，也就是拦得住。三条全过才算可用。改完任一环节，用同一组问题再自检。

## 允许长的方向与代价

加节点或边类型之前，先用现有的四种东西把同一件事表达一遍。写不出来，是真的缺；写得出来只是别扭，就不缺。

换存储允许，条件是 check 的召回行为不变——它仍然要在动手前把相关规则送到你面前。

Skill 与命令行的分工不要打乱：Skill 管怎么想，命令行管记住什么。把三个动作的判断写进命令行，或者把存储逻辑写进 Skill，都会让两边各长一半，往后谁也改不动。

## 改动走偏的判据

一条命令不再一一对应动作，比如一条命令同时做了拆解和固化，或者 check 的提醒不再发生在动手之前，闭环就断了。见到这两种情况，先退回设计这一层看，别在实现里打补丁。
