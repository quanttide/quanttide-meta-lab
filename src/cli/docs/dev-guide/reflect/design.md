# 设计

## 核心与三个动作

反思就是把结论拆成前提，检验前提，把修正后的前提固化成规则。

结论是当时以为对的东西，通常正是出问题的那一个，比如「AI 这次的实现符合我的意图」。结论不会单独成立，它压着若干没写出来的前提，比如「AI 理解的『提醒』和我理解的是同一件事」。前提一塌，结论就塌；错误几乎都藏在没写出来的前提里，挖出它们是第一步。

拆解从一个结论出发，写下它依赖的一到三条前提。检验拿反例去打每一条前提，有反例的标为可疑，没反例的保留。固化把可疑前提连同反例改写成一条可执行的规则存起来，下次遇到同类事件由 `reflect check` 提醒。

三个动作里，检验是唯一的真检验。没有反例的反思只是在确认自己本来就信的东西，等于没做。宁可这一步粗糙，也不能跳过；只拆不验的花架子没有价值。

## 三种节点两条边

结论、前提、规则三种节点，加结论到前提的依赖边、规则到前提的修正边。

反思里别处常见的要素都能落回这几种，不需要第五种。必要条件与充分条件只是「检验前提」的一种问法；框架识别就是更底层的前提；弱点标记是反复出现的坏前提，也就是规则的反面；触发器属于查询逻辑，归命令行，不属于数据。

节点少是为了让流程真的跑得动。每多一种节点，录入时就多一次判断；判断一多，人就懒得记，记不下来就无从检验。

## 五条命令

`reflect add` 记结论，`reflect dep` 记依赖，`reflect test` 录反例并标记可疑前提，`reflect commit` 固化成规则，`reflect check` 检索相关规则并提醒。三个动作加一次检索，正好五条，不再多也不再少。

存储先用一个 JSON 文件。图数据库能做的，一个文件加几行读写也做得完，而文件可以被 diff、被手工改、被一眼看穿。等 check 的召回真的不够用了再换，那时有真实数据，换得有依据。

## 规格为什么这么写

`reflect_spec.md` 的规格格式针对偏离的三个断点。

词汇断点：你嘴里的「提醒」是到点弹一次窗，AI 理解成企业级通知系统。规格用 vocabulary 把词钉死，再列 NOT 显式禁止它自己发挥。

规模断点：不说复杂度上限，AI 默认往完备方向建模。规格用 scope 给出文件数、概念数的上限。

边界断点：不说「不要什么」，AI 就把能想到的都要了。NOT 与 must_not 把不要的东西写明白。

代码模块的规格写成契约：意图、边界、不变量，分别回答要什么、多大、什么永远成立。测试模块的规格写成断言：场景、期望、不要测什么。两者共用同一套问法，只是落到不同对象上。

## 被砍掉的写法

伪代码、散文、UML 都不做规格载体，它们要么不能机械检查，要么藏得住含糊。

规格里也不另立「必要性检查」「找替代解释」这类名目：它们是检验前提的问法，不是独立动作。多一个名目就多一次分叉，分叉多了流程就走不到检验那一步。
