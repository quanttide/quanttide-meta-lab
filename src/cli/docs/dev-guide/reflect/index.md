# reflect 开发指南

这套文档写给接手 reflect 的人。AI 写错代码好办，一跑就知道。麻烦的是另一种情形：AI 建了一个模型，跟你脑子里想的不是一回事；它能跑，看着也像样，但你看得出「不对」，说不出哪里不对，也说不清它是怎么走到那一步的。reflect 把这个不可见的过程记下来，让偏离点可查，并把修正固化成下一次动手前的约束。

一句话概括：反思就是把结论拆成前提，检验前提，把修正后的前提固化成规则。

## 工程分解

按变更频率切，有一条稳定的缝。数据怎么记，几乎不变；怎么把记下的东西召回来，会换好几次；命令和交互是壳，随时能换；规范和规格是文档，不写代码。于是分成五个小项目，加一次验收。

存储负责三种节点两条边，以及一个 JSON 文件的读写。它变更最少，其余项目都依赖它。

召回负责给一个事件找出相关规则。第一版用词面匹配，以后可能换成嵌入或图查询，换的时候存储与命令都不动。

命令行负责五条命令，编排存储与召回，处理终端交互。它是壳。

反思规范负责拆解、检验、固化三个动作，规定每一步问什么、写到什么程度算完。文档，不写代码。

规格格式负责动手前交给 AI 的模板，代码模块用契约、测试模块用断言。文档，不写代码。

验收把五件合起来，放到真实工程环境跑一次，看偏离有没有被提前拦住。

## 依赖与顺序

依赖单向：存储 ← 召回 ← 命令行。反思规范与规格格式不依赖代码，只依赖存储约定的记法。验收依赖全部。

动手顺序按风险，不按层次。整套东西最不确定的一环是召得回——规则记下来了，下次动手前到底能不能被送到面前、能不能改变行为。所以先做最薄的一条：手工往 JSON 里写一条规则，让 check 命中它，证明这一环成立；再补记录侧，把五条命令写全；最后把规范与规格成文，做一次验收。

各项目一篇。`cli.md`（命令壳）与 `storage.md`（存储机制）讲的是工具本身，放在上一级 `docs/dev-guide/`；本目录是 reflect 这个模块的建模：`index.md`、`recall.md`、`skill.md`、`spec.md`、`eval.md`。

设计草稿在 `docs/dev-guide/`：`reflect.md` 是设计正本，`reflect_spec.md` 是规格格式，`reflect_test.md` 是开发场景的验证用例。当前任务在 `TODO.md`。
