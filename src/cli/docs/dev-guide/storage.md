# 存储

存储只管一件事：决定反思记下来的东西长什么样，并把它写进文件。代码在 `src/store.rs`。

## 记什么

只有规则。一条规则是修正后的前提，写成可执行的句子。

一条规则两个字段。文本是它的身份，比如「收编是否有利，取决于是否要求闭嘴」；`revises` 是它修正的前提，比如「收编=失去独立性」。

存的前提不是给程序推理用的，是给召回补词的：规则的句子未必带全下次事件里会出现的词，它修正的那句前提往往带着。

## 存档长什么样

存档是一个 JSON 文件，默认 `reflect.json`，用 `--store` 换路径。文件不存在时按空表处理，不报错。

```json
{
  "rules": [
    {
      "text": "收编是否有利，取决于是否要求闭嘴",
      "revises": ["收编=失去独立性"]
    }
  ]
}
```

没有前提的规则不写 `revises`，手改文件也不会把结构改坏。

## 对外的方法

`Store::load` 读，`Store::save` 写，其余方法只动内存。写入侧只有 `commit_rule`：同一条规则再固化一次，不会变成两条，新前提并进去，重复的不写第二遍。读取侧只有 `rules`，把整张表交出去。

`commit_rule` 只认文本做身份，所以改一条规则的措辞等于新记一条。

## 为什么用单个文件

图数据库能做的，一个文件加几行读写也做得完，而文件可以被 diff、被手工改、被一眼看穿。等召回真的不够用了再换，那时手上有真实数据，换得有依据。

## 边界

存储不判断哪条规则该被召回，那是召回的事；不决定什么时候写，那是命令行的事。它只认记法。

## 验收

`tests/cli.rs` 的用例覆盖这一层：`commit_persists_a_rule` 落盘一条规则，`commit_keeps_the_premises_it_revises` 留住前提，`committing_the_same_rule_again_merges_premises` 保证不重复。
