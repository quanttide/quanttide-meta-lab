# 存储

存储只管一件事：决定反思记下来的东西长什么样，并把它写进文件。代码在 `src/store.rs`。

## 记什么

三种节点。结论是当时以为对的东西，比如「被收编对IP不利」。前提是结论压着、却没写出来的东西，比如「收编=失去独立性」。规则是修正后的前提，写成可执行的句子，比如「收编是否有利，取决于是否要求闭嘴」。

两条边。结论指向前提，表示依赖；规则指向前提，表示修正。

节点的身份是类型加文本，文本相同、类型不同的两条互不覆盖。边不存 id，起点和终点直接写节点文本，方向由边的类型定。

别处常见的反思要素都能落回这几种。必要条件与充分条件只是检验前提的一种问法；框架识别就是更底层的前提；弱点标记是反复出现的坏前提，也就是规则的反面；触发器属于查询逻辑，归命令行，不属于数据。节点少是为了让流程真的跑得动：每多一种，录入时就多一次判断，判断一多，人就懒得记，记不下来后面全废。

## 存档长什么样

存档是一个 JSON 文件，默认 `reflect.json`，用 `--store` 换路径。文件不存在时按空存档处理，不报错。

```json
{
  "nodes": [
    { "kind": "claim", "text": "被收编对IP不利" },
    {
      "kind": "premise",
      "text": "收编=失去独立性",
      "counterexample": "分析师转顾问，信息更准、公信力没掉",
      "suspect": true
    },
    { "kind": "rule", "text": "收编是否有利，取决于是否要求闭嘴" }
  ],
  "edges": [
    { "kind": "depends_on", "from": "被收编对IP不利", "to": "收编=失去独立性" },
    {
      "kind": "revises",
      "from": "收编是否有利，取决于是否要求闭嘴",
      "to": "收编=失去独立性"
    }
  ]
}
```

`suspect` 与 `counterexample` 只有前提会有，取默认值时不再写出，所以手改文件也不会把结构改坏。

## 对外的方法

`Store::load` 读，`Store::save` 写，其余方法只动内存。写入侧是 `add_claim`、`add_dependency`、`add_counterexample`、`commit_rule`；读取侧是 `rules`、`suspect_premises`、`revised_premises`、`dependent_claims`。写入侧遇到不存在的节点会顺手补上，重复的边不会写第二遍。

`commit_rule` 的第二个参数为空时，修正当前全部可疑前提。这条默认是给 `reflect commit <规则>` 一条命令走完用的，要指定就传 `--revises`。

## 为什么用单个文件

图数据库能做的，一个文件加几行读写也做得完，而文件可以被 diff、被手工改、被一眼看穿。等召回真的不够用了再换，那时手上有真实数据，换得有依据。

## 边界

存储不判断哪条规则该被召回，那是召回的事；不决定什么时候写，那是命令行的事。它只认记法。

## 验收

`tests/cli.rs` 的三个用例覆盖这一层：`add` 落盘一条结论，`dep` 建出两个节点加一条边，`test` 标可疑并留住反例。
