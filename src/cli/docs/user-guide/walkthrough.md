# 走一遍

这一篇用一个例子把五条命令从头敲到尾。例子是真的：一次「AI 建的模型跟你想的不是一回事」。

## 出什么事了

你让 AI 写一个「任务提醒」功能，原话就一句：用户给任务设个时间，到点提醒一下。

它交回来一整套东西：Task、Schedule、Notification、Channel、Template、RetryPolicy，几十个文件。你能看出不对，但说不清哪里不对，也说不清它为什么走了这么远。

## 第一步：把结论写下来

先记下当时的判断。写的不是你后来想清楚的版本，是你当时真信的那句。

```bash
reflect add "AI实现符合我的意图"
```

```text
已记下结论：AI实现符合我的意图
```

## 第二步：拆出它依赖的前提

问自己一句：这句话要成立，得先有什么是真的？写下你觉得最要紧的一到三条。

```bash
reflect dep "AI实现符合我的意图" "AI理解的提醒=我的提醒"
reflect dep "AI实现符合我的意图" "AI会把复杂度和需求规模匹配"
```

```text
已记下依赖：AI实现符合我的意图 ——依赖——► AI理解的提醒=我的提醒
已记下依赖：AI实现符合我的意图 ——依赖——► AI会把复杂度和需求规模匹配
```

前提写到三条就够了。写到四五六条，通常说明结论本身还没想清楚。

## 第三步：每条前提去找一个反例

反例是这一整套里唯一算数的东西。没有反例的反思，只是在确认自己本来就信的。

```bash
reflect test "AI理解的提醒=我的提醒" --counterexample "AI加了 RetryPolicy、Channel、Template，我根本没提"
reflect test "AI会把复杂度和需求规模匹配" --counterexample "我只说了一句话，它建了几十张表"
```

```text
已标为可疑前提：AI理解的提醒=我的提醒
反例：AI加了 RetryPolicy、Channel、Template，我根本没提
已标为可疑前提：AI会把复杂度和需求规模匹配
反例：我只说了一句话，它建了几十张表
```

反例写具体发生了什么，不要写「可能不成立」这种话——那是判断，不是反例。

## 第四步：改写成一句提醒

把可疑前提和它的反例，压成一句你下次看得懂的提醒。这句提醒要能被找回来，所以句子里带上你下次会遇到的那类词。这次偏离留下两句：

```bash
reflect commit "让AI写功能前先给复杂度预算：最多几个文件、几个概念"
reflect commit "需求里的抽象词必须先钉死边界"
```

```text
已固化规则：让AI写功能前先给复杂度预算：最多几个文件、几个概念
修正的前提：AI理解的提醒=我的提醒
修正的前提：AI会把复杂度和需求规模匹配
已固化规则：需求里的抽象词必须先钉死边界
修正的前提：AI理解的提醒=我的提醒
修正的前提：AI会把复杂度和需求规模匹配
```

没写 `--revises` 时，每条规则都会挂到当时全部可疑前提上。想只挂到指定前提，就写 `--revises "前提"`。

## 第五步：一个月后，动手前先问一句

你又要让 AI 写一个「用户积分」功能。动手前先跑一次 `check`，把这次要做的事说给它。

```bash
reflect check "让AI写用户积分功能，抽象词和边界要说清"
```

```text
命中（25%）：需求里的抽象词必须先钉死边界
  词：ai、抽象、象词、边界
命中（19%）：让AI写功能前先给复杂度预算：最多几个文件、几个概念
  词：ai、功能、让
```

你被拦住了。在 AI 动手之前，你先把条件补上：「只要一个字段加一次加减，最多一个文件。」

「词」那一行是把中文按相邻两字切出来的碎片，用来算吻合度的，不用读。比例也一样，只用来排序。

顺手看一眼无关的事会不会误报：

```bash
reflect check "数据库连接池配置"
```

```text
没有命中规则。
```

## 之后

攒下的东西都在 `reflect.json` 里。不给事件跑一次 `check`，会列出全部规则：

```bash
reflect check
```

```text
规则：让AI写功能前先给复杂度预算：最多几个文件、几个概念
规则：需求里的抽象词必须先钉死边界
```
